# Debug Root Cause — BUG 根因分析

## The Iron Law

```
NO DIAGNOSIS WITHOUT BACKWARD TRACING FIRST
```

如果你没有逐层追踪到"正确输入→错误输出"的转换点，你不能声称找到了根因。猜的根因 = 没有根因。

## 输入

| 输入 | 说明 |
|------|------|
| BUG 描述 | 失败用例的原始信息，原样引用 |
| 预期行为列表 | design.md / layouts 确认的正确行为，逐条列出，每条含验证描述 |
| BUG 复现测试路径 | 失败的测试用例（后端 API 测试脚本 / 前端 E2E 用例） |
| output_path | debug-analysis.md 的写入路径（多用例循环时每个用例独立文件，如 `{task_dir}/.work/debug-analysis-{case}.md`） |
| before_attempts | `{task_dir}/.work/fix-attempts.md` 的路径。存在则读取——已验证为错误的路径，诊断时避开 |

## 流程

### 步骤 1：确认 BUG 存在

**跑 BUG 复现测试，捕获确切的失败输出：**

```bash
{test_runner} {test_path}
```

记录：
- 哪个 assertion 失败了
- actual vs expected 值是什么
- 完整的 traceback / 响应内容（如有）
- 前端 E2E：失败截图保存路径

**判定：** 测试 PASS（BUG 不存在）→ 停止诊断，结论写入 `{output_path}`。可能是环境问题或 BUG 已被修复。

**步骤 1 硬门（强制执行）：** 未完成以下全部项前，不得进入步骤 2。

| # | 检查项 | 状态 |
|---|--------|------|
| 1 | 复现测试已执行，失败输出已捕获（含 assertion 失败详情、actual vs expected、traceback/响应） | ✅ / ❌ |
| 2 | 如有截图证据（前端 E2E）：截图已保存并已查看实际渲染状态；如不适用（后端 API）：标注 N/A | ✅ / ❌ / N/A |
| 3 | debug-analysis.md 的 "证据链" §1 已写入上述测试输出（非 "代码 reading 确认"） | ✅ / ❌ |

**任何 ❌ → STOP。** 尚未确认 BUG 存在——你还没有可运行的失败起点，无法进行逆向追踪。

### 步骤 2：逆向追踪

**如 `before_attempts` 路径对应的文件存在：** 先读取——这些是已验证为错误的根因假设和修复路径。诊断时主动避开这些方向，从新的角度追踪。

**核心原则：永远不在症状点修。从失败点出发，逐层往上追，直到找到"正确输入变成错误输出"的转换点。**

```
失败点（测试 assertion 失败 / traceback 异常 / 响应不符合预期）
    ↓
问：什么代码直接产生了这个错误？
    ↓ 读这段代码
问：这段代码接收了什么输入？输入正确吗？
    ↓
    ├── 输入正确，输出错误 → 根因在这一层，停止追踪
    └── 输入本身就是错的 → 往上追一层：谁产生了这个错误输入？
                              ↓
                              重复
```

**每层只做一个判断：给定输入，这段代码的输出正确吗？**

- 输出正确 → 问题在上游，继续追
- 输出不正确 → 这一层就是根因位置

**追踪技巧：**

- 从 traceback 的最后一帧（最深层）开始，逐帧往上读调用链
- 对每个函数/方法：看它接收的参数 → 看它的逻辑 → 判断输出是否正确
- 数据流问题（值不对）：追谁设置了这个值 → 谁传给了它 → 一直追到赋值源头
- 控制流问题（走到了错误分支）：追哪个条件判断导致了错误分支 → 那个条件为什么为真/假
- 前后端联调问题：响应不符合预期 → 追后端接口逻辑 + 请求参数；渲染不符合预期 → 追前端组件 + 它调用的 API 及返回数据

**阅读代码时：**

- 不只读报错的那一行，读完整的函数/方法
- 关注变量赋值、条件分支、循环边界
- 如果调用链跨文件，用 Grep 追踪符号引用

### 步骤 3：形成假设

追踪到根因位置后，用一句话表述：

```
"根因是 {代码位置} 中的 {具体逻辑/数据问题}，因为 {因果链}"
```

**好假设的特征：**
- 精确到具体代码行或逻辑表达式
- 能解释所有症状（包括测试捕获的和设计稿/设计要求对照出的）
- 能解释为什么预期行为没有发生

**假设不成立时：**
- 回到步骤 2，从新的角度重新追踪
- 检查是否有遗漏的调用路径或数据来源
- 最多 3 轮追踪，仍无结论则输出已知信息并标注不确定性，停止

### 步骤 4：最小验证

**此步骤不可跳过。跳过 = 违反 Iron Law。代码阅读不是验证——只有实验结果是验证。"根因很明显" 是自我合理化（见常见自我合理化表第 1 行）。必须执行。**

**用最小的临时修改验证假设，确认后立即撤销。**

```
1. 做最小修改（改一行、加一个条件、修一个赋值）
2. 跑 BUG 复现测试（方法同步步骤 1）
3. 全部 PASS → 根因确认
   任一 FAIL → 假设错误，回到步骤 2
4. 撤销临时修改（git checkout / 手动还原）
```

**验证修改是 hack——不要把它写成正式修复。** 它的唯一目的是确认"改这里，BUG 就消失"。

**步骤 4 硬门（强制执行）：** 撤销确认后才可进入步骤 5。

| # | 检查项 | 状态 |
|---|--------|------|
| 0 | 是否在 debug-analysis.md 中写了"跳过"或"无需"？若是 → 本轮诊断无效，返回步骤 2 | ✅ / ❌ |
| 1 | 临时修改的具体内容已记录（文件、行号、改动内容） | ✅ / ❌ |
| 2 | BUG 复现测试已执行，结果已记录（FAIL → PASS） | ✅ / ❌ |
| 3 | 临时修改已撤销（`git checkout` 或手动还原），`git diff` 确认工作区干净 | ✅ / ❌ |

**任何 ❌ → STOP。** 未验证的根因假设 = 猜测。猜测的根因写入 debug-analysis.md 会浪费自修复循环的轮次。

### 步骤 5：写入 debug-analysis.md

保存到 `{output_path}`：

```markdown
# 调试分析

## BUG 描述
{失败用例，原样引用}

## 预期行为
{预期行为列表，逐条列出}
1. {行为 1} — 验证: {验证描述}
2. {行为 2} — 验证: {验证描述}
3. ...

## 根因
{经步骤 4 验证的根因，精确到具体代码位置 + 因果链}

## 证据链
1. {证据 1：BUG 复现测试的失败输出（具体 assertion 失败 + 截图/渲染证据，如有）}
2. {证据 2：逆向追踪路径 — 从症状到根因的每一层}
3. {证据 3：最小验证结果 — 临时修改了什么，测试从 FAIL → PASS}
4. {证据 4：排除的替代假设（如有）}

## 影响范围
| 文件 | 问题 |
|------|------|
| xxx | {具体问题描述} |

## 修复方向
{修复方案的概要描述，一两句话。不写实现代码。}
```

## Red Flags — 停下来，回到步骤 2

如果你发现自己在想：

- "看代码就知道问题在哪了，不用一步步追"
- "这个 BUG 很简单，直接写结论吧"
- "很可能就是 X 的问题，先写了再说"
- "追踪太慢了，我先猜一个再验证"
- "traceback 已经很清楚了，不需要逐层读"
- "这里不太对，但说不上来为什么——先跳过"
- 还没跑测试就开始写 debug-analysis.md
- 步骤 2 没追完就开始写根因

**以上任一条出现 → STOP。回到步骤 2，从失败点重新追。**

## 常见自我合理化

| 借口 | 现实 |
|------|------|
| "BUG 很简单，不需要完整追踪" | 简单 BUG 也有根因。跳步 = 猜。 |
| "traceback 已经告诉我在哪了" | traceback 告诉你症状在哪，不是根因在哪。 |
| "我见过类似的，我知道原因" | 类似不是相同。每个 BUG 用自己的证据链说话。 |
| "来不及追踪了，先给结论" | 猜的根因会浪费自修复循环更多轮次。 |
| "测一下就能确认，不用读代码" | 测试告诉你"哪里不对"，代码告诉你"为什么不对"。两者都要。 |

## 找不到根因时

如果 3 轮追踪后仍无法确认根因：

1. 你已经完成了流程——不是你偷懒
2. 输出已知信息：追踪到了哪一层、卡在哪一层、为什么卡住
3. 标注不确定性，写入 `{output_path}`

**但：** 大部分"找不到"的情况是步骤 2 追得不够深。卡住之前，先检查：是否读完了每个相关函数的完整代码？是否追到了赋值源头？

## 硬约束

- **不实施修复。** 步骤 4 的临时修改必须撤销。debug-analysis.md 不含实现代码。
- **测试 PASS 不代表没有 BUG。** 步骤 1 测试 PASS 时，检查测试是否真正覆盖了 BUG 场景。
- **最多 3 轮追踪。** 3 轮仍无结论 → 输出已知信息，标注不确定性，停止。
- **不猜测。** "可能是 X" 不写入 debug-analysis.md——只记录已验证的结论。
