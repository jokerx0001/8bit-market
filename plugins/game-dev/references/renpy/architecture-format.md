# Ren'Py architecture.md 格式规范

此文件定义 per-task `architecture.md` 的输出格式。architecture skill 的 `--task` 模式按此模板产出。

```markdown
# 架构设计

## 1. 模块关系图

[Mermaid flowchart：模块划分 + 数据流向]

### 模块职责一览

| 模块 | 职责 | 对应领域概念 |
|------|------|-------------|
| {模块 A} | {一句话职责} | {domain-design.md 中的模式/概念} |
| {模块 B} | {一句话职责} | {domain-design.md 中的模式/概念} |

## 2. 模块规约

对每个模块，按以下结构展开。

### 2.1 {模块名}

**领域来源：** 对应 domain-design.md 中的 {领域模式/概念}。{一句引言说明此模块在领域模型中的位置}。

**职责：** {一句话——这个模块做什么，不做什么。说清楚边界。}

**技术映射：**

- {引擎构造 1} → 实现 {领域行为/概念}，理由：{为什么选这个而非替代方案}
- {引擎构造 2} → 实现 {领域行为/概念}
- 核心配置/数据结构：{列出关键的配置项或数据定义，说明它们在代码中的形态}

**对外接口：**

| 方向 | 接口 | 说明 |
|------|------|------|
| 对外暴露 | {标签/方法/回调} | {调用方是谁、参数含义、调用时机} |
| 外部依赖 | {依赖的模块/数据源} | {获取什么数据、何时获取} |

**行为契约：**（如模块有状态机/生命周期）

{状态流转描述或状态图。关键边界行为——如输入为空时、依赖缺失时、异常路径时。}

**设计理由：** {关键的取舍——为什么选方案 A 而不是方案 B。如果没有明显的两难选择则省略。}

### 2.2 {模块名 B}
...

## 3. 运行时视图

### 关键流程

{用 Mermaid 序列图展示跨模块的关键场景。至少覆盖：正常路径 + 一个关键异常路径。}

### 状态机总览

{如果多个模块有状态机，在此汇总。若状态机已在模块规约中完整描述则不需要重复。}

## 4. 跨模块约定

- {约定 1}：{说明，如错误处理策略、资源生命周期管理、duck-type 契约}
- {约定 2}：{说明}

### 与现有架构的契合点

{本次设计如何融入现有项目架构——复用哪些模式、避免哪些冲突、不修改哪些系统。}

## 5. 架构决策记录

| # | 决策 | 替代方案 | 理由 |
|---|------|---------|------|
| 1 | {选择方案 X} | {方案 Y} | {为什么 X 更好} |
| 2 | ... | ... | ... |
```

## 内容规则

**必须遵守：**
- 技术映射标注理由
- 对外接口标注调用方和时机
- 序列图覆盖正常路径 + 至少一个异常路径

**禁止内容：**
- 引擎无关的领域分析（那是 domain-design 的职责）
- Screen 内部实现细节（那是详细设计的职责）
- RPY 代码片段——架构不写实现代码
